# IaC Template Constitution — Client Project

This constitution extends the global `constitution.md`. All rules in that document apply unchanged. The rules below are additive — they govern how a project uses `@iac-template/core`.

---

## 1. Scenario First — Always

Before any implementation decision, identify and document the scenario:

- **E1 — Full AWS**: the project controls all its infrastructure. AWS CDK manages everything via template library constructs.
- **E2 — Hybrid with integration**: AWS infrastructure is managed by the template; external systems not owned by this project are referenced as parameters (endpoint URL or secret ARN), never as CDK resources.
- **E3 — Client-constrained infrastructure**: the client controls their own server (VPS or on-premise). No template construct is instantiated. The environment is emulated via `docker-compose.yml` generated by `E3Generator`.

The scenario is declared once in `spec.md` and must not change during implementation without a documented architectural decision.

---

## 2. Constructs Over Raw CDK

For any responsibility covered by `@iac-template/core`, use the library construct. Never write raw CDK for:

- Relational databases → `DataLayerRelational`
- Non-relational databases → `DataLayerNonRelational`
- Lambda-based integration → `IntegrationLayerLambda`
- Container-based integration → `IntegrationLayerContainer`
- BFF / authenticated API → `PresentationLayerBFF`
- Static site / CDN → `PresentationLayerStaticSite`

If a construct does not cover the requirement, document the gap before extending it or writing raw CDK.

---

## 3. Controlled Vocabulary

Use this vocabulary in `spec.md` and `plan.md`. The `/speckit.plan` skill maps these terms to constructs automatically.

| Vocabulary term | Construct activated |
|---|---|
| `data layer: relational engine` | `DataLayerRelational` |
| `data layer: non-relational engine` | `DataLayerNonRelational` |
| `integration layer: functions mode` | `IntegrationLayerLambda` |
| `integration layer: containers mode` | `IntegrationLayerContainer` |
| `presentation layer: BFF mode` | `PresentationLayerBFF` |
| `presentation layer: static site` | `PresentationLayerStaticSite` |
| `external system integration: [name]` | `externalIntegrations` parameter on integration construct |
| `access: public / authenticated / internal-network` | `securityLevel` parameter on `PresentationLayerBFF` |
| `no template infrastructure` | No constructs — E3 scenario, use `E3Generator` |

---

## 4. E2 Rules

- External systems are declared as `externalIntegrations: [{ name, endpointSecretArn }]` on the integration construct.
- No CDK resource is created for the external system — not a Lambda, not a Secret, not an endpoint.
- `TemplateStack` does not distinguish E1 from E2 at runtime. The only difference is that E2 has `externalIntegrations` non-empty in at least one integration construct.

---

## 5. E3 Rules

- No `TemplateStack` is instantiated. No construct from the three layers is used.
- `E3Generator` is a plain utility class — it does not extend `Construct` and has no dependency on `aws-cdk-lib`.
- `E3Generator.generate()` validates runtime × allowed libraries compatibility before writing any file.
- The generated `docker-compose.yml` goes into `docker/docker-compose.yml`.

---

## 6. Non-Negotiables Specific to This Template

- **Cognito is always a parameter, never created by the project.** Pass `userPool` to `PresentationLayerBFF`; do not instantiate `UserPool` inside a project construct.
- **`app.ts` is the sole composition root.** No construct is imported from another construct file directly.
- **`OperationMode` is immutable.** Set once in the `TemplateStack` constructor; no setter, no conditional mode switching at runtime.
- **No secrets in code.** Use Parameter Store or Secrets Manager ARNs as construct parameters.
- **Stack outputs follow the library contract.** Never invent a different output format — use the `CfnOutput` keys defined by each construct.
